## 一、原始需求复述

用户对现有「销售订单系统」提出 5 项功能变更：

1. 销售端只展示活体售卖金额，不计入用品金额。
2. 财务端逻辑不对：销售端复制订单信息后订单跳转到财务待办，此时状态为"即将到店"，待财务点击"已成交"时弹出价格栏（活体售卖金额、用品、利润），此刻订单状态显示成已成交。
3. 地图展示页左下角加城市订单 TOP 排名、右下角加销售 TOP 排名（按订单数量排名）；左上角显示今日到店数量、右上角显示今日成交订单数量；地图居中；所有字体配色要有科技未来感。
4. 财务导出订单详单为空白，需要把订单的详细列都能导出成 Excel。
5. 管理员账户下能一键导入数据（之前历史的角色、订单信息）。

### 已与用户确认的 4 个决策点（本 PRD 的设计基线，不可推翻）

| 编号 | 决策 |
| --- | --- |
| **Q1 利润** | 财务在价格栏**手动输入**利润金额，直接存入 `dealProfit`。**不自动计算，不新增成本字段**。 |
| **Q2 成交流程** | **合并为一步**。订单处于「即将到店」(`pending_visit`) 时，财务直接点「已成交」即弹出价格栏（活体/用品/利润），成交即视为已到店（同时置 `visited` + `visitAt` 与 `closed` + `dealAt`）。**去掉单独的「确认到店」弹窗**。 |
| **Q3 金额范围** | 仅将**管理员销售看板的营收指标 + 销售排行金额列**改为只算活体金额 `dealLiveAmount`。**销售自己的订单列表本期不改**。 |
| **Q4 文件格式** | 导出与导入**统一用 Excel(.xlsx)**。订单详单导出 xlsx；历史数据（角色 + 订单）也用 Excel 模板导入。 |

## 二、变更目标概述

> **一句话目标**：把"钱怎么算、单怎么成交、数据怎么进出、地图怎么看"这四件事从"能用"做到"对且好用"。

| # | 目标 | 说明 | 正交性 |
| --- | --- | --- | --- |
| **G1 口径统一** | 管理层看到的业绩口径 = 活体金额，并让利润数据真正落库 | 解决"用品金额虚高业绩"与"`dealProfit` 建了字段却永远为 null"两个问题 | 数据/口径层 |
| **G2 流程收敛** | 财务成交动作从「两步两弹窗」压缩为「一步一弹窗」 | 降低财务操作成本，消除"确认到店"与"确认成交"状态错配 | 业务流程层 |
| **G3 数据可进出** | 订单详单可导出 Excel、历史数据（角色+订单）可 Excel 导入 | 打通系统与线下 Excel 的双向通道，解决"导出为空白"的硬伤 | 数据管道层 |
| **G4 展示升级** | 地图页升级为科技风"作战大屏"：四角信息 + 居中地图 | 满足展示/汇报场景 | 展示层 |

## 四、五项变更逐条说明

### 变更 1｜销售业绩口径改为"只算活体金额"

| 项 | 内容 |
| --- | --- |
| **需求原文** | 销售端只展示活体售卖金额，不计入用品金额 |
| **确认边界** | Q3：**仅改管理员销售看板的营收指标 + 销售排行金额列**；销售自己的订单列表本期不改 |

**变更前**
- `GET /api/stats`（`server.js:630`）：`revenue = closed.reduce((s,o) => s + (o.dealAmount||0), 0)`，`dealAmount = 活体 + 用品`
- ranking（`server.js:635`）：`sm[id].revenue += (o.dealAmount||0)`，并 `sort((a,b) => b.revenue - a.revenue)`
- 看板营收卡片、销售排行金额列均显示"活体+用品"合计

**变更后**
- 看板「营收」指标改用 **`liveRevenue`**（`dealLiveAmount` 累加，接口已有该字段，**无需新增计算**）
- 销售排行「金额」列改用 **`liveRevenue`**，且**排序依据同步改为 `liveRevenue` 倒序**（否则会出现"金额列乱序"的观感 bug）
- 文案明确标注为「**活体营收**」，避免管理员误解口径
- `dealAmount` / `supplyRevenue` **字段保留**，不删不改，仅前端不再作为主指标展示

**影响面**
- 后端：`GET /api/stats` ranking 排序字段（1 处）；`stats` 各周期无需改动（`liveRevenue` 已存在）
- 前端：看板营收卡片、趋势图 revenue 系列、销售排行表金额列
- **风险**：趋势图 `trend[].revenue` 目前也是 `dealAmount` 累加（`server.js:633`），需一并改为活体口径，否则卡片与趋势图对不上 → **属于本变更范围**
- **不影响**：销售端订单列表、财务端弹窗、导出数据（导出保留全部金额列）

### 变更 2｜财务成交流程合并为一步 + 新增利润录入

| 项 | 内容 |
| --- | --- |
| **需求原文** | 订单跳转到财务待办时状态为"即将到店"，财务点"已成交"即弹出价格栏（活体、用品、利润），此刻状态显示成已成交 |
| **确认边界** | Q1 利润手动输入存 `dealProfit`；Q2 合并为一步，成交即视为到店，去掉单独「确认到店」弹窗 |

**变更前**
- 财务必须走**两步**：① 打开 `visitModal` 点「确认到店」→ `POST /visit` 置 `visited`；② 再打开 `dealModal` 点「确认成交」→ `POST /deal`
- `POST /api/orders/:id/deal`（`server.js:607`）**硬校验** `if (o.visitStatus !== 'visited') return 400 '未到店'`
- `dealModal` 仅有「活体金额 + 用品金额 + 合计」，**无利润输入**
- `POST /deal` 只接收 `liveAmount`/`supplyAmount`，**`dealProfit` 永远为 null**

**变更后**
- 财务跟进页对 `pending_visit`（即将到店）订单**直接展示「已成交」主按钮**，点击即弹出**价格栏**
- 价格栏字段：**活体售卖金额** / **用品金额** / **利润**（三个独立数字输入）+ 合计展示（合计 = 活体 + 用品，仅展示，不含利润）
- 提交后后端**一次性**完成：
  - `visitStatus = 'visited'`、`visitAt = now`（若原本为空）
  - `dealStatus = 'closed'`、`dealAt = now`
  - `dealLiveAmount` / `dealSupplyAmount` / **`dealProfit`（新增落库）** / `dealAmount = 活体 + 用品`
- `POST /deal` **放宽前置校验**：允许 `visitStatus ∈ {'pending_visit', 'visited'}` 发起成交；仍拒绝 `null` 与 `not_visited`
- **「未成交」路径保留**：财务仍可标记 `not_closed`（此时**不**强制置 visited，`dealAmount = 0`）
- 「确认到店」弹窗（`visitModal`）**前端入口下线**；`POST /api/orders/:id/visit` 接口**保留**（兼容历史数据修正与 admin 兜底）
- 「复制订单信息」功能从 `visitModal` **迁移到订单行操作区**，避免随弹窗一起消失

**🎁 附加收益：顺带修复一个存量线上 bug**
> `renderOrders()` L466 对 `pending_visit` 订单**已经**渲染了「确认成交」按钮（admin/finance 可见），但后端 L607 硬校验 `visitStatus === 'visited'` → **管理员/财务在订单管理页点这个按钮必然报"操作失败"**。这是当前线上就存在的缺陷。P0-3 放宽校验后该 bug **自动消失，零额外工作量**。

**影响面**
- 后端：`POST /api/orders/:id/deal` 校验逻辑 + 字段写入（新增 `profit` 入参）
- 前端：`finance-follow` 页按钮渲染逻辑、`dealModal` 表单、`visitModal` 下线、复制订单信息挪位
- **数据一致性**：合并后 `visitAt` 与 `dealAt` 将高度接近（同一次提交），需求 3 的"今日到店"口径因此仍然成立
- **兼容存量**：已是 `visited` 但未成交的历史订单，走新流程时 `visitAt` **不覆盖**（保留原到店时间）
- **不影响**：销售报单流程、订单可见性规则

### 变更 4｜替换财务导出实现，输出真正的 Excel 详单

| 项 | 内容 |

### 变更 5｜管理员一键导入历史数据（Excel）

| 项 | 内容 |
| --- | --- |
| **需求原文** | 在管理员账户下能一键导入数据，之前历史的角色、订单信息 |
| **确认边界** | Q4：用 Excel 模板导入 |

**变更前**
- **无任何导入能力**。仅有 `migrate-to-cloud.js` 脚本（本地→云的一次性迁移工具，非用户可操作功能）
- 无文件上传中间件

**变更后**
- 管理员新增「**数据管理**」功能区（挂在看板页 header 或账号管理页，见待确认项 A5），包含：
  - 「下载导入模板」按钮 → 下载带表头与示例行的空白 .xlsx 模板
  - 「导入 Excel」按钮 → 选择文件上传 → 预校验 → 展示结果摘要
- **模板结构（定稿：单文件三 Sheet）**：
  - **Sheet1 `用户`**：账号(username) / 姓名(name) / 角色(**仅接受 `销售` / `财务`，不接受管理员**，见 A13) / 初始密码(可留空→取默认常量，见 A14)
  - **Sheet2 `订单`**：与变更 4 导出的 19 列**完全同构**（导出的文件可直接改完再导回，形成闭环）
  - **Sheet3 `填写说明`**：只读，承载枚举值（到店/成交状态中文对照）与校验规则，用于降低导入报错率
- **导入处理规则**：
  1. **两阶段执行**：先全表校验，**全部通过才写库**；任一行不合法则整体拒绝并返回错误清单（行号 + 原因）
  2. **用户去重**：以 `username` 为唯一键
  3. **订单去重**：以 `orderNo` 为唯一键
  4. **销售关联**：订单表按「销售人员姓名」匹配用户表 `name`，匹配不到则记为警告并落 `salesPersonName` 文本、`salesPersonId` 置空
  5. **中文状态反向映射**：已到店→`visited` 等，与导出映射对称
  6. **ID 生成**：导入订单沿用现有规则生成 `id`（`ORD` + 时间戳 + 序号，需保证批量导入内不重复）
  7. **默认策略**：**跳过已存在（合并新增）**，不覆盖不删除（见待确认项 A3）
  8. **结果反馈**：返回 `{ 成功新增 N 条, 跳过重复 M 条, 校验失败 K 条, 写入失败 J 条, 警告 W 条, 失败明细[], 使用默认密码的账号清单[] }`
     > ⚠️ **「校验失败」与「写入失败」必须分开统计**，原因见 A16：存储层会吞掉写入异常，只统计校验结果会给出虚假的成功数。
  9. **角色白名单**：角色列仅接受 `销售` / `财务`；填「管理员」→ 校验失败，提示「不支持导入管理员账号，请联系系统维护人员手动创建」（A13）
- **安全限制**：`requireRole('admin')`；文件 ≤ 5MB；仅接受 `.xlsx`；单次 ≤ 2000 行

**影响面**
- 依赖：**需新增文件上传中间件**（`multer`，内存存储即可）+ Excel 读库（与变更 4 复用 `exceljs`）
- 后端：新增 `POST /api/import/xlsx`、`GET /api/import/template.xlsx`
- 前端：新增数据管理入口 + 文件选择 + 结果弹窗
- **风险（已解除）**：密码存储经核实为**明文**（`server.js:465` 直接比对），导入按明文写入即可，与现有机制一致。密码加密改造列为技术债 TD-1，本期不做
- **风险**：导入是唯一会批量写库的操作，务必先做 JSON 备份（可复用旧 `GET /api/export`）

## 五、用户故事

### 销售（sales）
1. **As a** 销售，**I want** 一键报单后订单自动进入财务待办，**so that** 我不用再单独通知财务确认到店。
2. **As a** 销售，**I want** 我的业绩在管理层看板中按活体金额计算，**so that** 用品金额不会虚增/干扰我与同事的横向对比。

### 财务（finance）
3. **As a** 财务，**I want** 对"即将到店"的订单直接点「已成交」就弹出价格栏，**so that** 我不用先点"确认到店"再点"确认成交"，少一半操作。
4. **As a** 财务，**I want** 在价格栏里除活体、用品外还能手填利润，**so that** 利润数据能真正沉淀进系统而不是记在我自己的表里。
5. **As a** 财务，**I want** 一键把订单详单导出成 Excel，**so that** 我能直接拿去做对账和月报，不用手工抄录。

### 管理员（admin）
6. **As a** 管理员，**I want** 看板营收与销售排行只统计活体金额，**so that** 我看到的业绩口径与公司考核口径一致。
7. **As a** 管理员，**I want** 一块科技风的地图大屏，四角能同时看到今日到店、今日成交、城市 TOP、销售 TOP，**so that** 我在晨会/汇报时一屏讲清全局。
8. **As a** 管理员，**I want** 用 Excel 模板一键导入历史角色与订单，**so that** 系统上线时能承接过去的存量数据，而不是从零开始。

### 8.1 产品决策说明（A13 / A14）

#### A13｜导入模板「角色」列 —— **决策：不允许导入管理员，仅接受 `销售` / `财务`**

**背景**：`POST /api/users`（`server.js:483`）硬编码 `role: 'sales'`，账号管理页按钮也是「+ 新建销售账号」→ 系统当前**没有任何界面能创建 admin/finance 账号**（F4）。若导入放开管理员，它将成为系统里第一个、也是唯一一个能批量制造管理员的入口。

**决策理由**：
1. **风险不对称**：禁止管理员 → 万一真要加，人工 seed 一次，成本 5 分钟；允许管理员 → 一行 Excel 误填/被篡改即获系统最高权限，成本是全量数据泄露。两者量级完全不同。
2. **符合需求本意**：用户说的是"导入之前历史的角色、订单信息"——历史要承接的是**销售与财务团队成员**及其订单。管理员通常只有 1–2 个，属于系统级账号，本就不该走批量通道。
3. **不破坏既有安全边界**：admin 账号目前靠 seed 数据带出，这是事实上的权限边界，增量需求不应顺手拆掉它。
4. **可逆**：这是一条校验规则，日后若确需放开，改动量极小。先收紧再按需放开，优于反向。

**实现要求**：角色列填「管理员」的行 → 校验失败，错误信息明确写「**不支持导入管理员账号，请联系系统维护人员手动创建**」，而非笼统的"角色非法"。

> 同时暴露一个待办：`POST /api/users` 硬编码 `role:'sales'` 导致财务账号也无法通过界面创建。**本期不修**（超出 5 项变更范围），登记为技术债。

#### A14｜默认密码 —— **决策：沿用 `123456`，但必须抽为 `config.js` 常量**

**决策理由**：
1. 系统密码本就**明文存储**（A8 确认），此时纠结默认密码复杂度属于"在漏水的船上擦地板"——真正的风险敞口是明文存储，已单独登记为技术债。
2. 使用者是销售/财务一线人员，导入后需口头/微信告知账号密码，复杂密码会显著增加沟通与输错成本。
3. `123456` 与系统现有安全姿态一致，不引入新的认知负担。

**实现要求（三条，缺一不可）**：
- 默认密码抽为 `config.js` 单一常量（如 `DEFAULT_IMPORT_PASSWORD`），改动无需翻代码；
- 导入结果摘要**必须列出使用默认密码的账号清单**，管理员据此逐个通知；
- 导入结果弹窗显著提示「**请通知相关人员尽快修改密码**」。

**关联 P2 建议**：系统当前无"首次登录强制改密"机制，已补入 P2-8。

> A13 / A14 均为**低成本可逆**决策（一条校验规则 + 一个常量），架构师**可按此直接实施**，无需等待用户回复；若用户最终有不同意见，调整成本 < 30 分钟。

### 8.2 产品决策说明（A15 / A16）

#### A15｜导入前备份 —— **决策：不强制手动下载，改为服务端自动快照并设为硬闸门**

**问题**：导入前是否强制管理员先下载一份备份？

**决策：不强制手动下载（维持"提示但不强制"），但把原 P1-6 的服务端自动备份升级为 P0-15，并设为硬闸门——备份失败则导入中止。**

**理由——"强制手动下载"是个错误的工具**：
1. **自动优于强制手动**。手动可以被忘记、被跳过、下载完找不到文件；服务端快照拿到的必然是**导入前的精确状态**，用户什么都不用做。
2. **强制手动会退化成安全剧场**。管理员连做 5 次修正导入就要下 5 个文件，一个都不会打开，只会形成点击疲劳，然后开始找绕过的办法。摩擦买不到安全。
3. **真正的风险不是"忘了备份"**，而是 A16 的静默半成功——这个是手动下载完全防不住的。

**同时必须认识到备份的真实价值边界**（A3 已定合并新增+跳过重复，导入不删不改）：
- 云端模式 `addItem` 是 `coll.add()` **纯追加**，最坏结果是多出些行，可人工删除，**不会丢已有数据**；
- 但**本地模式** `addItem` 是 `push` + `writeAll` 的**全文件覆写**（`server.js:342-343` → `fs.writeFileSync`），一次 2000 行导入 = 2000 次全量重写，**进程中途挂掉会留下截断的 JSON**，这才是真正会丢数据的路径。

因此备份的必要性成立，但正确形态是**自动 + 前置阻断**，而非让用户点一下下载。

**实现要求**：
- 导入正式写库前，服务端先落一份带时间戳的全量快照到 `data/backup/`；
- **快照写入失败 → 直接返回错误、终止导入**，不允许"备份失败但继续导入"；
- 前端仍保留"建议先备份"的文案提示（不拦截），并在结果弹窗告知本次快照文件名，便于回滚时定位。

#### A16｜静默半成功 —— **决策：必须校验写入返回值，摘要区分「校验失败」与「写入失败」**

**这是本轮新发现的缺陷，此前双方均未识别。**

PRD 原写的"先全表校验、全部通过才写库"**只防住了坏数据，没防住失败的写入**。存储层会吞异常：
- `addItem` 捕获异常后 `return null`（`server.js:332-338`），调用方不检查返回值就完全无感；
- `writeAll` 捕获后仅 `console.error` 然后 `return`（`server.js:305`）；
- 云端 `writeAll` 更是 **delete-all-then-add 非原子操作**（`server.js:301-303`），两个循环之间失败即数据全失。

**后果**：校验通过 486 行 → 实际只写进 200 行 → 摘要照样显示"成功新增 486 条"。管理员据此认为导入完成，**错误要到很久以后对账时才会暴露**，届时已无法定位。这比导入直接报错严重得多。

**实现要求**：
- 每行写入**必须检查返回值**（`addItem` 返回 `null` 即视为失败）；
- 摘要中「**写入失败 N 条**」为**独立字段**，不得与校验失败合并；
- 写入失败的行须进入失败明细（含行号与订单号/账号），支持 P1-4 导出后重传；
- 只要 `写入失败 > 0`，结果弹窗须以**警示态**呈现，不得显示为绿色成功。

> A15 / A16 均属**数据安全底线**，建议不接受降级或延后。

## 九、验收标准（整体）

1. **口径一致性**：管理员看板营收卡片、趋势图、销售排行三处的营收数字，在同一时间口径下必须完全一致，且均等于活体金额之和。
2. **流程完整性**：新建订单 → 销售报单 → 财务一步成交（含利润）→ 订单状态显示「已到店 + 已成交」→ 导出 Excel 中该订单利润列有值。全链路可跑通。
3. **数据闭环**：导出的订单 xlsx，不做任何修改直接导入，系统应识别为"全部重复、跳过 N 条、新增 0 条"，不产生脏数据。
4. **样式隔离**：地图页改造后，切换到看板/订单/账号管理等页面，样式与改造前**完全一致**（无污染）。
5. **权限正确**：finance 可导出 Excel 但不可导入；sales 无导出无导入；admin 全部可用。
6. **【v1.1 新增】导出必须含已成交单**：财务导出的 xlsx 中，**已成交订单必须在内**（这是原缺陷②的直接回归验证点）。用一条已成交订单验证：导出文件里能查到它，且金额/利润/成交时间列均有值。
7. **【v1.1 新增】Excel 格式合法**：导出文件用 Excel 打开**不得弹出"格式与扩展名不符"警告**（原实现是 HTML 伪装 .xls）；金额列可直接被 `SUM()` 求和。
8. **【v1.1 新增】跨时区正确性**：将系统时间设为北京时间 00:30 造一条到店订单，地图大屏「今日到店」应 **+1**（验证未落入"昨天"）。
9. **【v1.1 新增】破千不失真**：造 1000+ 条订单，看板总数、地图城市合计、导出行数三者一致，无静默截断。
10. **【v1.1 新增】管理员导入拦截**：导入模板中角色列填「管理员」的行，必须校验失败并给出明确提示，**不得建成 admin 账号**。
11. **【v1.2 新增】备份硬闸门**：人为使 `data/backup/` 不可写，发起导入 → 必须**直接失败并提示备份未成功**，且库中**无任何新增记录**。
12. **【v1.2 新增】写入失败不虚报**：人为让部分行写入失败（如注入存储层异常），摘要中「写入失败」数必须准确，「成功新增」数**不得包含失败行**，弹窗呈警示态。
